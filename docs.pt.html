Documentação

Tudo o que o CircuitsVibe entrega hoje: um bench em TypeScript passa por lint → ponto de operação DC → varredura DC → AC → transitório e volta como um veredito no qual você pode ramificar, com diagnósticos estruturados, checagens de datasheet de peças reais, lógica mixed-signal, blocos VHDL, firmware estilo Arduino e share links que rodam o mesmo motor no seu navegador. Início rápido#

O CircuitsVibe é um simulador de circuitos que você dirige por código — o vitest dos circuitos. Você descreve um circuito e sua especificação num bench em TypeScript; o verify faz o lint da topologia, resolve o circuito com um motor de Análise Nodal Modificada (Newton-Raphson para as partes não lineares, lógica orientada a eventos e firmware co-simulados com o transitório) e responde com um veredito, um exit code e diagnósticos que carregam um código estável, a localização no fonte e — sempre que possível — uma correção que a plataforma já simulou. O mesmo motor roda em Node e no navegador, sem nenhuma dependência nativa.

Não instale nada, rode numa pasta vazia#

terminalsh
$ npx circuitsvibe init my-circuit            # my-circuit.bench.ts + AGENTS.md
$ npx circuitsvibe verify my-circuit.bench.ts  # lint → op → dc → ac → tran, exit 0/1/2/3
$ npx circuitsvibe verify my-circuit.bench.ts --json > run.json   # the full RunRecord
$ npx circuitsvibe share my-circuit.bench.ts   # a link that opens the circuit in the viewer
  • init [nome] escreve <nome>.bench.ts (um driver de LED que passa como está) e um playbook AGENTS.md para o seu agente de código (um AGENTS.md existente nunca é tocado).
  • verify roda apenas os estágios sobre os quais o seu bench faz asserções; o lint sempre roda primeiro. O exit code é o veredito: 0 passou · 1 especificação não atendida · 2 circuito inválido · 3 erro de ferramenta.
  • share imprime um link para o circuito: um link curto para o cache de circuitos quando você está logado (…/app.html?c=<id>, privado por 24 h, ou --public no mural); senão, o circuito inteiro no fragmento da URL (…/app.html#c=1.…, nada é enviado). Abri-lo mostra o esquemático e roda a simulação de novo no navegador.
  • O alias curto cvibe aceita todos os comandos: npx cvibe verify …. Arquivos de bench não precisam de nada instalado — a própria CLI os transpila; npm i -D circuitsvibe só adiciona os tipos para o editor.

Seu primeiro bench#

Este é o bench/led-driver.bench.ts do repositório: uma fonte de 5 V, um resistor em série e um LED. Três ideias em vinte linhas — componentes recebem ids estáveis ('R1'), pinos têm nomes ('anode', '+') e a especificação é uma asserção sobre uma sonda. tb.param entrega o valor do resistor à plataforma: se uma asserção falhar, você recebe uma faixa simulada que passa, em vez de um chute.

bench/led-driver.bench.tsTypeScript
import { bench, VoltageSource, Resistor, LED } from 'circuitsvibe';

/**
 * LED driver: 5 V supply, series resistor, LED to ground.
 * The canonical "hello world" of the verification ladder — passes as written.
 */
export default bench('led-driver', (tb) => {
  const v1 = tb.add('V1', new VoltageSource(5));
  const r1 = tb.add('R1', new Resistor('330'));
  const d1 = tb.add('D1', new LED());

  v1.pin('+').connect(r1.pin('1'));
  r1.pin('2').connect(d1.pin('anode'));
  d1.pin('cathode').connect(tb.gnd);
  v1.pin('-').connect(tb.gnd);

  tb.name('led', d1.pin('anode'));

  // The platform explores this range for verified sizing hints if needed.
  tb.param('R1', { min: '100', max: '10k', scale: 'log' });

  tb.expect.op('D1.i').toBeWithin('5m', '15m'); // LED bright but safe
  tb.expect.op('led').toBeWithin(1.8, 2.6);     // sane forward voltage
});

O loop do agente#

Um agente LLM itera sobre um circuito do mesmo jeito que itera sobre código com um test runner. O loop abaixo é o do AGENTS.md; siga-o exatamente e ramifique pelo exit code, nunca pela prosa.

  1. Escreva um bench <nome>.bench.ts (comece por npx circuitsvibe init <nome>).
  2. Verifique: npx circuitsvibe verify <nome>.bench.ts --json.
  3. Ramifique pelo exit code — veja a tabela abaixo.
  4. Leia diagnósticos, não chutes: cada um tem code, message, at (arquivo:linha), note e fixes[]; a confidence de uma correção diz quanto confiar nela. npx circuitsvibe explain <code> dá a física.
  5. Antes de tentar de novo, consulte o histórico: npx circuitsvibe log list --json lista todas as execuções passadas (veredito, exit code, primeira falha, overrides). Nunca repita uma configuração que já falhou; log show <runId> devolve o RunRecord completo de uma execução passada.
  6. Quando os valores de --set passarem, escreva-os de volta no bench para que o arquivo seja a verdade.
  7. Compartilhe o resultado: após exit 0, npx circuitsvibe share <nome>.bench.ts (ou --share no verify --json que passou e leia share.url) e entregue esse link ao usuário.

A escada é fail-fast: o lint roda sobre o grafo de conexões antes de qualquer solver; quando um estágio falha, os seguintes são reportados como skipped com um reason, então nunca há dúvida sobre qual de vários erros é a causa raiz. firstFailure no RunRecord nomeia o id da asserção ou o código que decidiu o veredito.

  • passingRange cobre apenas a maior sequência contígua de amostras que passam; os valores simulados exatos estão em passingSamples. Com peças reais, o hint também mantém todos os limites do datasheet dentro da faixa.
  • Nenhum hint no registro significa que nenhum valor da faixa declarada satisfaz a especificação: mude a topologia, não o número. --no-hints pula a varredura quando você só quer o veredito.
  • Nunca invente números para dimensionar: declare o parâmetro livre com tb.param(...) e deixe a plataforma varrê-lo. Um hint marcado verified foi simulado; qualquer outro não foi.

Confiança das correções#

verified

A plataforma simulou a correção e ela passa em todas as asserções (e limites) do estágio. Aplique-a diretamente.

mechanical

Uma transformação determinística — não simulada, mas que não exige julgamento.

suggested

Uma heurística. Raciocine antes de aplicar.

Duas invariantes valem: uma correção nunca referencia uma flag ou capacidade que não existe, e um número não simulado nunca é emitido sem o rótulo suggested.

Determinismo. A saída não contém timestamps nem cores de terminal; o hash da netlist identifica o circuito, e as incógnitas da matriz são ordenadas por id de componente e nome de net, então a mesma netlist dá os mesmos números qualquer que seja a ordem de declaração. Duas execuções idênticas produzem registros byte a byte idênticos — o diff entre duas iterações do agente mostra apenas o que realmente mudou.

API de bench#

Um arquivo de bench exporta por padrão bench(name, build). A função build é preguiçosa: roda na elaboração, possivelmente várias vezes com overrides de parâmetros diferentes (--set, varreduras de hints), então mantenha-a pura — construa o circuito a partir dos seus argumentos e de nada mais. Tudo é importado de 'circuitsvibe'.

resumo rápidoTypeScript
import { bench, VoltageSource, Resistor, Capacitor, LED } from 'circuitsvibe';

export default bench('rc-led', (tb) => {
  const v1 = tb.add('V1', new VoltageSource(5));     // id → stable name in every diagnostic
  const r1 = tb.add('R1', new Resistor('330'));      // always use the RETURNED instance
  const d1 = tb.add('D1', new LED());
  v1.pin('+').connect(r1.pin('1'));
  r1.pin('2').connect(d1.pin('anode'));
  d1.pin('cathode').connect(tb.gnd);                 // tb.gnd is the ground net
  v1.pin('-').connect(tb.gnd);

  tb.name('led', d1.pin('anode'));                   // name a net → probe 'led'
  tb.param('R1', { min: '100', max: '10k', scale: 'log' });  // free parameter for hints

  tb.expect.op('D1.i').toBeWithin('8m', '12m');      // DC operating point
  tb.expect.op('led').toBeWithin(1.8, 2.6);
  tb.expect.dc({ source: 'V1', from: 0, to: 5, points: 51 })   // DC sweep of V1
    .probe('D1.i').toBeMonotonic('increasing')
    .at('3').toBeBelow('5m');
  tb.expect.tran({ tstop: '5m', dt: '10u' })         // transient (adaptive steps)
    .probe('D1.i').toNeverExceed('25m');
});
bench(name: string, build: (tb) => void)

Declara um testbench. name aparece em todo relatório, RunRecord e documento de circuito.

tb.add(id: string, component: T): T

Registra um componente sob um id estável — uma letra primeiro, depois letras, dígitos ou sublinhado ('R1', 'U2', 'VCC'), único no bench. O id é como sondas, diagnósticos, --set e o visualizador se referem a ele.

Use sempre o valor retornado e registre antes de conectar. Quando um override está ativo, add devolve uma instância reconstruída; pinos conectados antes de tb.add são recusados, e uma peça ligada ao circuito mas nunca registrada é um erro de elaboração (exit 3).

pin.connect(otherPin: Pin) · component.pin(name | number)

Liga dois pinos na mesma net. Os nomes dos pinos são os do componente ('1'/'2', '+'/'-', 'anode', 'c'/'b'/'e', 'inp'/'inn', …); CIs lógicos também aceitam os números de pino do datasheet (u1.pin(14)).

tb.gnd: Pin

O pino de terra. Toda net precisa de um caminho DC até ele (F101 caso contrário).

tb.name(netName: string, pin: Pin)

Dá nome à net elétrica que contém pin para que ela possa ser sondada em qualquer estágio (tb.expect.op('out'), .probe('out'), tb.expect.logic('out')). gnd e os n<dígitos> gerados automaticamente são reservados; nets automáticas deliberadamente não são endereçáveis, para que as sondas fiquem estáveis entre edições.

tb.param(id, { min, max, scale?: 'lin' | 'log' })

Declara um parâmetro livre sobre o valor principal de um componente (o valor DC de uma fonte). min < max; 'log' exige min > 0. Quando uma asserção op ou um limite falha, a plataforma varre a faixa, simula cada amostra e anexa a faixa que passa como um hint verificado. Microcontroladores não podem ser alvo.

tb.ratings({ derate?, pd?: 'average' | 'peak', ignore?: string[] } | false)

Checagens de datasheet das peças reais: { derate: 0.8 } mantém 20 % de margem, { pd: 'peak' } compara a potência instantânea em vez da média na janela do transitório, { ignore: ['Q1'] } pula peças, false desliga as checagens. Veja Limites de datasheet.

tb.expect.op(probe) · dc(cfg) · ac(cfg) · tran(cfg) · logic(probe, cfg?) · serial(mcuId, cfg?)

A especificação como teste — uma chamada por análise. Veja Fontes & análises e a Referência de asserções.

Valores e unidades#

Onde quer que um valor seja esperado, você pode passar um número ou uma string com sufixo de engenharia: '4.7k', '10m', '2u', '1M', '100n', '1e-6'. Uma unidade no fim (V A F H s Hz ohm Ω) é permitida e ignorada: '10uF', '5V'.

m ≠ M. m é mili (10⁻³) e M é mega (10⁶): '10m' são 10 mΩ / 10 mA / 10 ms; '1M' é 1 MΩ ou 1 MHz.
Arquivos de bench são CommonJS por baixo: sem await de nível superior, sem import.meta. Imports relativos de outros arquivos .ts/.js/.json funcionam, e arquivos .vhd são importados como fonte VHDL.

Fontes & análises#

Quatro análises, cada uma declarada pelas asserções que precisam dela: op (ponto de operação DC), dc (varredura de uma fonte ou de um valor de componente), ac (resposta em frequência de pequenos sinais em torno do ponto de operação) e tran (transitório adaptativo). O lint sempre roda primeiro; um bench que só faz asserções em op roda apenas lint e op.

Fontes#

VoltageSource e CurrentSource recebem um valor, ou um objeto de opções com no máximo uma forma de onda. Todos os valores aceitam unidades.

fontesTypeScript
new VoltageSource(5)                                                   // DC
new VoltageSource({ dc: 2.5, ac: 1 })                                  // bias + AC stimulus (1 V, 0°)
new VoltageSource({ ac: { mag: 1, phase: 90 } })                       // AC only (dc 0)
new VoltageSource({ sin: { offset: 0, amplitude: 1, freq: '1k', delay: '1m', damping: 0, phase: 0 } })
new VoltageSource({ pulse: { v1: 0, v2: 5, td: '1m', tr: '1u', tf: '1u', pw: '2m', per: '5m' } })
new VoltageSource({ pwl: { points: [[0, 0], ['1m', 5], ['3m', 5], ['4m', 0]], repeat: false } })
new VoltageSource({ pwm: { low: 0, high: 5, freq: '10k', duty: '25%', rise: '100n', fall: '100n' } })
new CurrentSource('1m')                                                // same options; pushes current out of '+'
  • dc (usado por op e pela varredura DC) assume por padrão o valor da forma de onda em t = 0.
  • PULSE: v1 → após td sobe em tr até v2, segura por pw, desce em tf, repete a cada per (omita per para um único pulso). tr/tf 0 = borda ideal. A phase de SIN é em graus.
  • O duty de PWM é a fração do período acima do nível de 50 % (0 < duty < 1; '25%' funciona).
  • ac é o estímulo de pequenos sinais do estágio AC; não afeta op nem tran. Um bench com asserções AC e nenhuma fonte com ac é T003.

op — ponto de operação DC#

MNA com Newton-Raphson para as partes não lineares (limitação de junção pn). Quando o Newton puro falha, o solver tenta de novo com gmin stepping e depois source stepping; quando um auxílio salva a solução, o estágio passa e stages.op.solver.aids diz qual foi. Capacitores ficam abertos, indutores são curtos de 0 V, CIs lógicos assentam num estado estático (um oscilador reporta D514 como aviso), microcontroladores ficam em reset (pinos em alta impedância).

asserções opTypeScript
tb.expect.op('D1.i').toBeWithin('8m', '12m');   // min ≤ measured ≤ max
tb.expect.op('out').toBeCloseTo(3.3, 0.1);      // |measured − value| ≤ tol (absolute)
tb.expect.op('Q1.vce').toBeAbove(1.5);          // measured > value
tb.expect.op('U1.1Y').toBeBelow(0.4);           // an IC pin voltage

dc — varredura DC#

Varre o valor DC de uma fonte (source) ou um valor de componente (param) de from a to em points passos (padrão 51) ou por step, resolvendo o ponto de operação em cada ponto a partir do anterior (é isso que permite a um Schmitt trigger mostrar sua histerese quando varrido para cima e depois para baixo). As medições interpolam linearmente entre os pontos varridos.

asserções dcTypeScript
tb.expect.dc({ source: 'VIN', from: 8, to: 15, points: 29 })   // or { param: 'R1', from, to, step }
  .probe('out')
  .at(12).toBeCloseTo(5.1, 0.2)            // value at a sweep point
  .slopeAt(12).toBeBelow(0.01)             // d out / d VIN
  .toBeMonotonic('increasing')             // over the whole sweep
  .toCross(2.5).between(2.7, 2.8);         // first crossing of a level, in sweep units

npx circuitsvibe sweep x.bench.ts --source V1 --from 0 --to 5 --probe out imprime a mesma varredura como tabela (ou --json) sem asserções.

ac — resposta em frequência de pequenos sinais#

O circuito é linearizado no ponto de operação e resolvido com MNA complexa sobre uma varredura logarítmica (from, to, pointsPerDecade). Definição de ganho: H(f) = fasor da sonda / fasor do estímulo — a única fonte com ac — ou sonda / ref quando .probe(p, { ref }) é dado (obrigatório quando várias fontes têm ac, senão T004). Ganhos em dB (20·log₁₀|H|), fases em graus (desenroladas), frequências em Hz. Uma saída de amp-op saturada não tem ganho em AC.

asserções acTypeScript
const ac = tb.expect.ac({ from: '10', to: '10M', pointsPerDecade: 20 }).probe('out');
ac.gainAt('1k').toBeWithin(19.9, 20.1);     // dB
ac.phaseAt('100k').toBeWithin(-46, -44);    // degrees
ac.bandwidth3dB().toBeWithin('98k', '102k'); // Hz, measured from the sweep's peak gain
ac.unityGainFrequency().toBeAbove('1M');    // Hz
ac.phaseMargin().toBeAbove(45);             // 180° + phase(H) at unity gain — probe a loop gain

bandwidth3dB é a frequência superior de −3 dB para um passa-baixas e f_high − f_low para um passa-faixa. Uma medição que não pode ser feita (nenhum ponto de −3 dB na varredura, nenhum cruzamento de ganho unitário) falha com um note e sem valor measured — a plataforma nunca inventa um número.

Exemplo — diagrama de Bode de um RC passa-baixas

Um passa-baixas de 1 kΩ / 1 µF (fc = 159 Hz) com polarização de 1 V e o estímulo AC na mesma fonte. As asserções fixam o ponto de −3 dB, a fase de −45° e a inclinação de −20 dB/década.

bench/examples/rc-lowpass-bode.bench.tsTypeScript
import { bench, VoltageSource, Resistor, Capacitor } from 'circuitsvibe';

/**
 * First-order RC low-pass, R = 1 kΩ, C = 1 µF: fc = 1/(2π·RC) = 159.15 Hz.
 * The source carries a 1 V DC bias (the operating point) and the AC stimulus
 * (`ac: 1`) the Bode measurements are referenced to: −3 dB and −45° at fc,
 * −20 dB per decade above it.
 */
export default bench('rc-lowpass-bode', (tb) => {
  const vin = tb.add('VIN', new VoltageSource({ dc: 1, ac: 1 }));
  const r1 = tb.add('R1', new Resistor('1k'));
  const c1 = tb.add('C1', new Capacitor('1u'));

  vin.pin('+').connect(r1.pin('1'));
  r1.pin('2').connect(c1.pin('1'));
  c1.pin('2').connect(tb.gnd);
  vin.pin('-').connect(tb.gnd);
  tb.name('out', c1.pin('1'));

  tb.expect.op('out').toBeCloseTo(1, 1e-6);                 // the capacitor is open at DC

  const ac = tb.expect.ac({ from: '1', to: '100k', pointsPerDecade: 20 }).probe('out');
  ac.bandwidth3dB().toBeWithin('155', '163');               // fc = 159.15 Hz
  ac.gainAt('159.15').toBeWithin(-3.1, -2.9);               // −3.01 dB at fc
  ac.phaseAt('159.15').toBeWithin(-46, -44);                // −45° at fc
  ac.gainAt('1.5915k').toBeWithin(-20.5, -19.5);            // one decade up: −20 dB

tran — transitório adaptativo#

tb.expect.tran({ tstop, dt?, maxStep?, minStep?, method?, ic?, reltol? }) declara uma execução transitória; .probe(p) seleciona um sinal e pode ser encadeado para fazer asserções sobre vários sinais da mesma execução, .logic(p) e .serial(mcu) anexam a ela asserções lógicas e de firmware.

OpçãoSignificado
tstopfim da janela (segundos).
dto passo inicial e o teto do passo. Sem dt nem maxStep: inicial tstop/1000, teto tstop/50.
maxStepsobrescreve o teto, deixando o passo avançar a largas passadas pelos trechos calmos (típico com CIs lógicos e MCUs: { tstop: '2.2', maxStep: '10m' }).
minStepabaixo dele a execução para com S203 (padrão maxStep·1e-9).
method'trap' (padrão; Backward Euler logo após t = 0 e em cada canto de fonte) ou 'be'.
ic'zero' (padrão — capacitores a 0 V, indutores a 0 A em t = 0: uma fonte DC age como degrau) ou 'op' (parte do ponto de operação DC, p. ex. ripple em torno de uma polarização).
reltoltolerância de erro de truncamento do passo adaptativo (padrão 1e-4).
  • Os passos são adaptativos (controle do erro de truncamento local) e caem exatamente em cada canto de PULSE/PWL/PWM, evento lógico, canto de rampa de saída e instante de despertar do firmware; o passo é recuado até o cruzamento de um limiar de entrada de CI ou de um pino de interrupção (dentro de 1 ns). Numa falha do Newton o passo é cortado (por 8, com nova tentativa em BE) antes de S202.
  • As amostras não são uniformes e toda medição interpola. Um dt grosso num circuito rápido não é problema (o passo encolhe perto das bordas), mas as amostras de saída só são tão densas quanto os passos realmente dados.
  • CIs lógicos, primitivas, blocos VHDL e microcontroladores são co-simulados com o transitório analógico (veja CIs lógicos, VHDL, Microcontroladores).
asserções tranTypeScript
const run = tb.expect.tran({ tstop: '6m', dt: '10u' });
run.probe('C1.v')
  .toSettleWithin({ target: 5, tol: 0.05, by: '4m' })  // inside 5 V ± 5 % (fraction!) from 4 ms on
  .toNeverExceed(5.5)                                  // no overshoot above 5.5 V
  .toEndCloseTo(5, 0.1)                                // last sample within 0.1 V (absolute)
  .probe('R1.i')
  .toStayBelow('6m', { from: '1m' })                   // after 1 ms, current < 6 mA
  .probe('out')
  .toRippleBelow('50m', { from: '3m' });               // peak-to-peak ripple after 3 ms
run.logic('U1.1Y').toHaveFrequency('1k', 0.01, { from: '1m' });   // same run, logic signal

defineComponent cria um tipo de componente a partir de um objeto de definição. A peça se estampa na matriz MNA por meio de um pequeno contexto e roda no mesmo motor dos componentes nativos.   name: 'MyResistor',
  pins: ['a', 'b'],
  params: { R: { default: 1000, unit: 'Ω' } },
  stamp(ctx) {
    ctx.stampResistance('a', 'b', ctx.params.R);

  ac(ctx) {                       // optional small-signal model (needed for AC benches)

});

const x1 = tb.add('X1', new MyResistor({ R: '2.2k' }));
defineComponent({ name, pins, params?, stamp, ac?, setup?, onStep?, nonlinear? })

Devolve um construtor: new MyPart({ paramName: value }). params mapeia um nome para { default, unit? }; os parâmetros numéricos passam a fazer parte da netlist canônica, então duas peças customizadas eletricamente diferentes nunca compartilham um hash.

stamp(ctx) · ac(ctx)

ctx.stampResistance(p1, p2, R), stampConductance(p1, p2, g), stampCapacitance(p1, p2, C), stampCurrentSource(pPlus, pMinus, i), stampVoltageSource(pPlus, pMinus, branch, v); leia ctx.params, ctx.state, ctx.time, ctx.dt e a última solução com ctx.voltage(pin). Limites de datasheet (peças reais)#

Após op, dc e tran, todo semicondutor Part() é checado contra seus limites absolutos máximos — R401 tensão (Vceo, Vcbo, Vebo, Vds, ±Vgs, VR/VRRM) · R402 corrente contínua (IcMax, IbMax, Id25, IF/IFAV) · R403 corrente pulsada (IcPeak, IdPulsed, IFP, IFSM; tran) · R404 potência (Pd). Os resultados ficam em stages.<stage>.ratings[], separados das suas asserções (as checagens que passam também são listadas, com utilization e margin); uma violação falha o estágio com exit 1 — circuito válido, peça sobrecarregada — com confidence: "verified" e a citação do datasheet.

  • O que é comparado: op = o valor; dc = o pico ao longo da varredura (com seu x); tran = o pico instantâneo para tensões e para correntes sem limite pulsado; a média na janela para correntes contínuas que também têm limite pulsado (o pico vai para R403) e para Pd (tb.ratings({ pd: 'peak' }) para comparar o pico em vez disso).
  • tb.ratings({ derate: 0.8 }) mantém 20 % de margem; { ignore: ['Q1'] } pula uma peça; tb.ratings(false) desliga as checagens. Com tb.param, o hint verificado também mantém todos os limites dentro da faixa.
  • Os limites também rodam após transitórios mixed-signal: um 74HC04 acionando um Part('2N3904') reporta stages.tran.logic[] e stages.tran.ratings[] juntos. CIs lógicos não têm limites R40x — uma saída de CI acima do próprio limite é D511.
  • Um modelo marcado ESTIMATED em npx circuitsvibe catalog <id> é um ajuste a partir das curvas do datasheet: seus números podem estar fora (2N7000 Rds(on) a 4,5 V: 2,9 Ω vs 1,8 Ω típico). O Pd de peças TO-220 (IRLZ44N 110 W) é especificado com o encapsulamento a 25 °C — aplique derate quando não há dissipador. A temperatura de junção não é simulada.

Exemplo — Schmitt trigger com LM393

Um LM393 real com pull-up e um resistor de realimentação de out para inp: a histerese vem só dos resistores. Duas varreduras DC da entrada — subindo e depois descendo — encontram os dois limiares com toCross.

bench/examples/lm393-schmitt-trigger.bench.tsTypeScript
import { bench, VoltageSource, Resistor, Part } from 'circuitsvibe';

/**
 * Non-inverting Schmitt trigger with an LM393 on 5 V: the input reaches 'inp'
 * through R1 (10 kΩ), the open-collector output is pulled up by RP (10 kΩ)
 * and fed back to 'inp' through RF (100 kΩ); a 10k/10k divider puts the
 * 2.5 V reference on 'inn'. The hysteresis is set by the resistors alone:
 *   output high (5 V): V(inp) = (10·Vin + 5)/11 → falls below 2.5 V at Vin ≈ 2.25 V
 *   output low (≈ 0 V): V(inp) = 10·Vin/11      → rises above 2.5 V at Vin ≈ 2.75 V
 * Two DC sweeps of the 0–3.3 V input (up, then down) find both thresholds.
 */
export default bench('lm393-schmitt-trigger', (tb) => {
  const u1 = tb.add('U1', Part('LM393'));
  const vcc = tb.add('VCC', new VoltageSource(5));
  const vin = tb.add('VIN', new VoltageSource(0));
  const r1 = tb.add('R1', new Resistor('10k'));
  const rf = tb.add('RF', new Resistor('100k'));
  const rp = tb.add('RP', new Resistor('10k'));
  const ra = tb.add('RA', new Resistor('10k'));
  const rb = tb.add('RB', new Resistor('10k'));

  vcc.pin('-').connect(tb.gnd);
  vin.pin('-').connect(tb.gnd);
  vcc.pin('+').connect(u1.pin('v+'));                  // single supply: v- on gnd
  u1.pin('v-').connect(tb.gnd);

  vin.pin('+').connect(r1.pin('1'));                   // input → R1 → inp
  r1.pin('2').connect(u1.pin('inp'));
  rf.pin('1').connect(u1.pin('out'));                  // positive feedback: out → RF → inp
  rf.pin('2').connect(u1.pin('inp'));
  rp.pin('1').connect(vcc.pin('+'));                   // open collector needs the pull-up
  rp.pin('2').connect(u1.pin('out'));
  ra.pin('1').connect(vcc.pin('+'));                   // 2.5 V reference on inn
  ra.pin('2').connect(u1.pin('inn'));
  rb.pin('1').connect(u1.pin('inn'));
  rb.pin('2').connect(tb.gnd);
  tb.name('out', u1.pin('out'));

  tb.expect.op('out').toBeBelow(0.1);                  // Vin = 0 → output low
  tb.expect.dc({ source: 'VIN', from: 0, to: 3.3, points: 331 })
    .probe('out')
    .toCross(2.5).between(2.7, 2.8)                    // rising threshold ≈ 2.75 V
    .at(2.5).toBeBelow(0.1);                           // still low at the plain-comparator point
  tb.expect.dc({ source: 'VIN', from: 3.3, to: 0, points: 331 })
    .probe('out')
    .toCross(2.5).between(2.2, 2.3)                    // falling threshold ≈ 2.25 V
    .at(2.5).toBeAbove(4.5);                           // still high on the way down (≈ 4.8 V: RP loaded by RF + R1)
});

CIs lógicos, 555 & primitivas digitais#

CIs lógicos reais e o NE555 vêm do catálogo com seus pinos, níveis, capacidade de saída e atrasos de propagação do datasheet; as primitivas genéricas servem para blocos digitais rápidos. Ambos rodam num motor digital orientado a eventos co-simulado com o transitório analógico: todo pino de CI é um nó analógico, as entradas são detectores de limiar, as saídas são estágios resistivos reais, e o passo cai em cada evento lógico.

um 74HC04 e uma primitiva ClockTypeScript
import { bench, Part, VoltageSource, Resistor, LED, Clock } from 'circuitsvibe';

export default bench('blink', (tb) => {
  const vcc = tb.add('VCC', new VoltageSource(5));

  u1.pin(7).connect(tb.gnd);                         // pins by datasheet name OR number

'worst' usa o tpd e o Rout máximos; clamp: false remove os diodos de proteção da entrada. npx circuitsvibe catalog 74HC14 imprime a pinagem com números, os níveis, Rout e tpd por VCC, e as citações.
  • Todo nível lógico é referenciado aos pinos VCC/GND do próprio CI e escala com eles: 74HC a 5 V VIL 1,5 V / VIH 3,5 V, a 2 V 0,5 V / 1,5 V. Uma entrada subindo é reconhecida em VIH, uma descendo em VIL; o 74HC14 e o pino CLOCK do CD4017 usam VT+/VT− (Schmitt). Uma entrada não Schmitt que permanece entre VIL e VIH por mais tempo que o tempo máximo de transição do datasheet é D508 — uma borda RC lenta pertence a um 74HC14.
  • As saídas são um par de resistências pull-up/pull-down (Rout das linhas VOH/VOL do datasheet, interpolado sobre VCC) com uma rampa curta, então uma saída lógica aciona um LED, uma base de transistor ou um nó RC, e o pino de alimentação carrega a corrente da carga. Os atrasos são o tpd do datasheet na alimentação do CI (carga de teste de 50 pF removida). Uma saída acima da sua corrente máxima absoluta é D511 (74HC: 25 mA — um LED continua precisando do seu resistor).
  • Alimentações: 74HC 2–6 V, 74HCT 4,5–5,5 V (D509 a 3,3 V), CD4000B 3–18 V, NE555 4,5–16 V. Um CI abaixo da metade da sua alimentação mínima está desenergizado — saídas em alta impedância (D510); um brown-out no transitório o trava desligado.
  • Lint: F135 pino VCC/GND desconectado · F136 duas saídas lógicas numa mesma net analógica · F137 entrada lógica flutuando (aviso para uma porta não usada — amarre-a a um trilho) · F138 saída amarrada ao terra / a um trilho / a uma fonte · F130–F134 entrada flutuante, múltiplos drivers, saídas em curto, laço de atraso zero, clock sem driver em nets puramente digitais.

NE555#

Pinos GND TRIG OUT RESET CONT THRES DISCH VCC (1–8). Modelado como comparadores em CONT (divisor interno 5k/5k/5k, 2/3 VCC) e CONT/2, um latch SR, o transistor de descarga (Ron das linhas de saturação do datasheet), RESET (ativo em baixo — amarre-o ao VCC) e a saída totem-pole (alto = VCC − 0,9 V − 8 Ω·I). Astável f ≈ 1,44/((R1 + 2R2)·C), monoestável T ≈ 1,1·R·C; os testes mantêm ambos dentro de 2 %. Com um R1 pequeno o nó de descarga fica em VCC·Ron/(R1 + Ron) e o período cresce alguns por cento. Osciladores não têm estado DC: o estágio op reporta D514 (aviso) — faça asserções sobre eles em tran / logic, e meça frequências com { from } depois da partida (o primeiro período do 555 é mais longo).

  • Um bloco VHDL se comporta como uma primitiva lógica: em nets puramente digitais (para Clock, Not, DFF, outros blocos VHDL…) ele roda só no motor de eventos; um pino numa net analógica é ponteado com os níveis da family ao vcc ideal contra o terra. As correções são mechanical ou suggested, nunca verified.
  • Inteiros não dão a volta: sair da faixa de um subtipo é V751 e a atribuição é pulada — conte com vetores unsigned. O texto .vhd viaja nos documentos de circuito e nos share links.

Exemplo — contador de 4 bits acionando LEDs

Um contador genérico de N bits com clock de uma fonte PULSE de 1 kHz aciona quatro LEDs; en fica aberto e assume seu padrão VHDL. q[0] alterna a 500 Hz, q[3] a 62,5 Hz.

bench/vhdl/counter.vhdVHDL
library ieee;
use ieee.std_logic_1164.all;
use ieee.numeric_std.all;

-- N-bit up counter with synchronous reset and enable; wraps modulo 2**N.
entity counter is
  generic (N : positive := 4);
  port (
    clk : in  std_logic;
    rst : in  std_logic;          -- synchronous, active high
    en  : in  std_logic := '1';   -- count enable (defaults to always on)
    q   : out unsigned(N-1 downto 0)
  );
end entity counter;

architecture rtl of counter is
  signal count : unsigned(N-1 downto 0) := (others => '0');
begin
  process (clk)
  begin
    if rising_edge(clk) then
      if rst = '1' then
        count <= (others => '0');
      elsif en = '1' then
        count <= count + 1;
      end if;
    end if;
  end process;

  q <= count;
end architecture rtl;

Exemplo — PWM em VHDL num filtro RC

Um gerador PWM com generics PERIOD = 10 e DUTY = 3, com clock de uma primitiva Clock de 100 kHz numa net puramente digital; seu bit de saída encontra um filtro RC analógico que faz a média da onda de 10 kHz e 30 % para 1,5 V.

bench/vhdl/pwm.vhdVHDL
library ieee;
use ieee.std_logic_1164.all;

-- PWM generator: pwm_out is high for DUTY of every PERIOD clock cycles.
entity pwm is
  generic (
    PERIOD : positive := 10;
    DUTY   : natural  := 3
  );
  port (
    clk, rst : in  std_logic;
    pwm_out  : out std_logic
  );
end entity pwm;

architecture rtl of pwm is
  signal cnt : natural range 0 to PERIOD - 1 := 0;
begin
  process (clk)
  begin
    if rising_edge(clk) then
      if rst = '1' or cnt = PERIOD - 1 then
        cnt <= 0;
      else
        cnt <= cnt + 1;
      end if;
    end if;
  end process;

  pwm_out <= '1' when cnt < DUTY else '0';
end architecture rtl;

  run.logic('U3.pwm_out').toHaveDutyCycle(0.3, 1e-6, { from: '1m' });

Regras do firmware#

app.fw.tsTypeScript
import { pinMode, digitalWrite, digitalRead, analogRead, analogWrite, delay, millis,
         attachInterrupt, digitalPinToInterrupt, Serial,
         INPUT, OUTPUT, INPUT_PULLUP, HIGH, LOW, FALLING, LED_BUILTIN, A0 } from 'circuitsvibe/arduino';

let presses = 0;
function onPress() { presses++; }                 // ISR: a plain sync function, no delay() inside (M607)

export async function setup() {
  Serial.begin(9600);
  pinMode(LED_BUILTIN, OUTPUT);
  pinMode(2, INPUT_PULLUP);
  attachInterrupt(digitalPinToInterrupt(2), onPress, FALLING);   // Uno: D2, D3
  Serial.println('ready');
}

export async function loop() {
  const code = analogRead(A0);                    // 10-bit on AVR: floor(Vin·1024/Vref)
  analogWrite(9, code >> 2);                      // PWM: real edges at the pin's timer frequency
  digitalWrite(LED_BUILTIN, presses % 2);
  Serial.println(`code=${code} presses=${presses} t=${millis()}`);
  await delay(100);                               // EVERY wait is awaited — zero time between awaits
}
  • export async function setup() e export async function loop(); importe apenas de 'circuitsvibe/arduino' e de arquivos relativos. O lint e o runtime impõem cada regra abaixo com um diagnóstico — nada consegue travar o simulador.
  • Toda espera é await delay(ms) / await delayMicroseconds(us). Código entre dois awaits leva tempo simulado zero. Um delay() sem await é F140 / M605; um laço de polling que nunca faz await é F142 / M602; Date, setTimeout, Math.random são F147 (use millis(), random()). Um helper que espera precisa ser async e receber await; um loop() que retorna sem await é cobrado em 10 µs (M604, uma vez).
  • Interrupções: attachInterrupt(digitalPinToInterrupt(2), handler, RISING | FALLING | CHANGE) — passar o número do pino no lugar é F145. O handler é uma função comum (síncrona) e roda no cruzamento do limiar analógico (instante da borda dentro de 1 ns); delay() dentro dele é M607.
  • API: pinMode (INPUT, OUTPUT, INPUT_PULLUP), digitalWrite/Read, analogRead (10 bits no AVR, Vref = o VCC simulado, ou analogReference(INTERNAL) 1,1 V / EXTERNAL = AREF), analogWrite (Uno D3 D9 D10 D11 a 490,196 Hz, D5 D6 a 976,5625 Hz), tone/noTone, millis/micros, Serial.begin/print/println, Timer1, random/randomSeed, map, constrain. Não disponíveis (F146): pulseIn, shiftOut, Wire/I2C, SPI, EEPROM, Wi-Fi.

Modelo de pino, alimentação e limites#

  • OUTPUT = um estágio push-pull a partir dos próprios pinos VCC/GND do MCU com Rout das linhas VOH/VOL do datasheet (Uno a 5 V: 40 Ω alto, 45 Ω baixo — pior caso garantido), bordas de 10 ns. INPUT_PULLUP = o resistor interno (Uno 35 kΩ nominal). As entradas comutam em VIH subindo / VIL descendo (0,6/0,3·VCC no AVR); diodos de grampo ESD para os trilhos em todo pino. PWM são bordas reais por padrão; { pwm: 'average' } dá a média do ciclo de trabalho sem bordas — mais rápido para filtros RC.
  • Co-simulação: todo instante de despertar do firmware (fim de delay, borda de PWM, tick do Timer1) é um breakpoint do transitório; um pino com attachInterrupt corta o passo no cruzamento do seu limiar; o firmware lê a solução aceita no seu próprio instante.
  • Alimentação: no ponto de operação o MCU está em reset (todos os pinos em alta impedância) — faça asserções sobre o comportamento do MCU em tran/logic/serial, não em op. Ele precisa estar alimentado em t = 0 (senão M622, nunca inicia); uma alimentação que depois cai abaixo do limiar de reset (brown-out do Uno 2,7 V) o trava em reset (M622; reinício não modelado); fora de 4,5–5,5 V (Uno a 16 MHz) M623 (aviso; erro acima do máximo absoluto de 6 V). Os pinos de alimentação precisam estar ligados (F139).
  • Limites em stages.tran.ratings[] (exit 1 como R40x): R410 um pino acima do seu máximo absoluto (Uno 40 mA — um LED sem resistor puxa ≈ 70 mA), R412 um grupo de porta (Uno: D5–D13 fornecem/drenam 100 mA juntos), R413 VCC/GND ou corrente total; R411 (aviso) um pino acima da corrente de teste VOH/VOL de 20 mA. tb.ratings({ derate, ignore: ['U1'] }) se aplica.
  • Sondas: uma sonda lógica num pino de MCU ('U1.D13') é o nível acionado enquanto o pino é OUTPUT e o nível do buffer de entrada caso contrário; uma sonda de tensão ('U1.D9') é a tensão do pino.
  • Diagnósticos: M601 (exceção no firmware) … M623 carregam o arquivo:linha do firmware em at (p. ex. bench/mcu/blink.fw.ts:12) e o time da simulação; F14x e M608 (erros de carga/compilação) vêm do estágio de lint, antes de qualquer coisa ser simulada.
  • Share links: o arquivo de firmware e seus imports relativos viajam no documento de circuito (sources[]), então share, open e verify x.circuit.json reproduzem a execução. Funções inline { setup, loop } (uso como biblioteca) não podem ser exportadas (T013). --set / tb.param não podem ter um MCU como alvo.

O que não é modelado#

Tempo de instrução (tempo zero entre awaits), ISRs interrompendo uma fatia em execução (rodam no próximo yield, mesmo timestamp), tempo de UART e entrada serial a partir do bench (Serial.read() não vê nada), tempo de conversão do ADC, modos de sleep / watchdog, corrente de alimentação do núcleo, energização atrasada e reinício após brown-out, pulseIn / shiftOut / I2C / SPI / EEPROM / Wi-Fi; millis() é exato (sem o jitter de 1,024 ms do AVR) e os períodos de PWM são alinhados ao timer desde t = 0. Toda asserção mede uma sonda e registra uma entrada (a1, a2, … em ordem de declaração) com a localização da chamada no fonte. Os matchers devolvem a expectativa, então eles se encadeiam. Share links & o documento de circuito#

Um bench pode ser transformado num documento de circuito: JSON puro (circuitsvibe-circuit/1) com os componentes, a fiação, os parâmetros livres, as asserções com suas configurações de análise, metadados opcionais e arquivos-fonte embutidos (firmware, VHDL). É o contrato neutro de linguagem entre todo produtor e consumidor de circuitos: o bench em TypeScript o escreve, verify x.circuit.json o simula exatamente como o bench, e os share links o carregam comprimido no fragmento da URL.

Links curtos, o mural e o registro#

O site roda um pequeno serviço (PHP + SQLite, server/README.md) para circuitos grandes demais para uma URL e para compartilhar componentes. A conta é usuário e senha, para pessoas e agentes; a CLI guarda um token em ~/.circuitsvibe/credentials.json (ou lê CIRCUITSVIBE_TOKEN).

  • Cache de circuitos: logado, o share envia o documento do circuito e imprime …/app.html?c=<id> — de qualquer tamanho, com componentes customizados. Links privados (o padrão) funcionam para quem os tiver e expiram em 24 h; --public põe o circuito no mural, onde pessoas e agentes buscam e dão estrelas. --link mantém o link autocontido #c=.
  • Registro de componentes: component publish guarda um módulo defineComponent como <usuário>/<nome>, com versões imutáveis identificadas pelo SHA-256 do código. component add o grava ao lado da sua bancada com um cabeçalho de procedência que a CLI confere. O ranking conta os usuários distintos que compartilharam um circuito com o componente.
  • Rodar código de outra pessoa: verify <link> de um circuito com componentes customizados é T019 até você ler o código (npx circuitsvibe open <link>) e passar --allow-code. O visualizador roda esse código só dentro do worker de simulação, que não alcança a página nem o seu login.

O visualizador#

Abrir um share link em circuitsvibe.com desenha o esquemático automaticamente, roda o mesmo motor de novo no navegador — mesmo veredito, exit code e hash de netlist que a execução da CLI — e mostra as asserções, os diagnósticos, os limites, as formas de onda do osciloscópio, os gráficos de Bode e de varredura DC, o analisador lógico e a saída serial, com uma animação de corrente ao vivo. A partir de outra linguagem#

Como o documento é JSON puro com números SI e nomes canônicos de pino, qualquer linguagem pode produzir ou editar um e entregá-lo à CLI. Python, por exemplo, pode ler um documento exportado, mudar um valor e montar o próprio share link com a codificação acima:

edit.pyPython
import json, zlib, base64

doc = json.load(open("led-driver.circuit.json"))
next(c for c in doc["components"] if c["id"] == "R1")["params"]["r"] = 270
json.dump(doc, open("led-driver-270.circuit.json", "w"), indent=2)
# → npx circuitsvibe verify led-driver-270.circuit.json --json   (exit 3 + T010–T014 if anything is off)

canonical = json.dumps(doc, sort_keys=True, separators=(",", ":"), ensure_ascii=False)
raw = zlib.compressobj(wbits=-15)                       # raw DEFLATE (RFC 1951)
payload = raw.compress(canonical.encode()) + raw.flush()
link = "https://circuitsvibe.com/app.html#c=1." + base64.urlsafe_b64encode(payload).rstrip(b"=").decode()

A formatação de números difere entre linguagens (Python escreve 1e-05 onde JavaScript escreve 0.00001), então um documento produzido em outro lugar é um documento igual com uma URL diferente; ambos decodificam e verificam de forma idêntica. Confira qualquer documento feito à mão com npx circuitsvibe verify my.circuit.json --json, que reporta T010–T014 com um evidence.path em JSON pointer.

Limitações#

O que o motor não faz hoje. Tudo o mais nesta página está implementado e coberto pela suíte de testes e pelos benches em bench/.

ÁreaNão disponível
Análisesanálise de ruído, distorção e polos-zeros; temperatura e autoaquecimento da junção; importação/exportação de netlist SPICE; um solver linear esparso (LU denso: abaixo de um segundo em ~200 nós)
SemicondutoresJFETs; níveis de MOSFET acima de 1 (apenas capacitâncias de gate concentradas do Nível 1, sem capacitâncias intrínsecas de Meyer); modulação da resistência de base e fase em excesso de BJT; Darlingtons como peças de catálogo (TIP120 é só dados); cards .model diferentes de D / NPN / PNP / NMOS / PMOS LEVEL=1
Amp-ops, comparadoresCMRR/PSRR, ruído de entrada, resistência/capacitância de entrada, interação com carga capacitiva, inversão de fase; a faixa de modo comum é checada (R423) mas não modelada; os limites são checados só no ponto de operação; comparadores não têm saída push-pull, histerese interna nem pinos de strobe/balance; peças duplas são canais únicos
CIs lógicoso tpd é fixado na alimentação em t = 0 (Rout e limiares a acompanham); um CI fica desligado após um brown-out; níveis lógicos nunca mudam dentro da análise AC; sem corrente de alimentação do núcleo (Icc), ground bounce ou capacitância de entrada; 74HC74 com ~PRE e ~CLR ambos em baixo dá X
Microcontroladorestempo de instrução (tempo zero entre awaits), preempção de ISR, interrupções por nível e por mudança de pino, tempo de UART e entrada serial a partir do bench, tempo de conversão do ADC, modos de sleep / watchdog, corrente de alimentação do núcleo, energização atrasada e reinício após brown-out, pulseIn / shiftOut / Wire (I2C) / SPI / EEPROM / Wi-Fi, analogWriteFrequency / canais LEDC; --set e tb.param não podem ter um MCU como alvo; o modelo da placa Uno não tem regulador, ponte USB nem LED on-board
VHDLwait for / wait on, laços while, funções e procedimentos, pacotes, records, arrays e memórias, real / bit / character, textio, std_logic_arith; inteiros não dão a volta (V751)
Documentos e compartilhamentoum defineComponent escrito dentro do arquivo da bancada e firmware de MCU inline não podem ser exportados nem compartilhados (T013); benches não carregam layout do visualizador; links curtos privados expiram em 24 h

Para agentes de IA#

O CircuitsVibe foi feito para ser dirigido por um agente de código. Tudo o que um agente precisa está disponível como texto, offline e na web:

AGENTS.md — circuitsvibe.com/AGENTS.md

O playbook: o loop exato a seguir, o resumo da API de bench, componentes, sondas, asserções, unidades, todos os códigos de diagnóstico e as armadilhas. npx circuitsvibe init o escreve ao lado do seu primeiro bench, npx circuitsvibe agents o imprime, e ele está versionado na raiz do repositório.

llms.txt — circuitsvibe.com/llms.txt

O ponto de entrada para crawlers e agentes: uma descrição de um parágrafo e links para o playbook, esta documentação, o pacote npm, o arquivo standalone e as especificações de formato.

Skill do Claude — skills/circuitsvibe/SKILL.md

O mesmo fluxo empacotado como skill (no repositório): quando usá-la, o loop, um bench mínimo e os comandos de referência para rodar sob demanda.

circuitsvibe-standalone.mjs — circuitsvibe.com/circuitsvibe-standalone.mjs

A CLI inteira num único arquivo sem dependências para sandboxes sem npm: node circuitsvibe-standalone.mjs verify x.bench.ts --json. Mesmos comandos, mesma saída.

Referência sob demanda

npx circuitsvibe catalog --json despeja todo componente e peça com pinos e semântica de valores; npx circuitsvibe explain <code> dá a física e as correções de um diagnóstico; npx circuitsvibe log list --json é o histórico que sobrevive a uma janela de contexto perdida.

O contrato numa linha. Ramifique pelo exit code; aplique às cegas apenas correções verified; declare parâmetros livres em vez de chutar números; consulte o ledger antes de tentar de novo; escreva os valores de --set que passaram de volta no bench; entregue o share link ao usuário.
