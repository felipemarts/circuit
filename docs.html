Getting started#

CircuitsVibe is an analog circuit simulator you drive from code — vitest for circuits. You describe a circuit and its spec in a TypeScript bench; verify simulates it with a Modified-Nodal-Analysis engine (Newton-Raphson for nonlinear parts) and answers with a verdict, an exit code, and diagnostics that carry a stable code, a source location and — where possible — a fix the platform has already simulated. The same engine runs in Node and in the browser, with zero native dependencies.

Install nothing, run in an empty folder#

terminalsh
$ npx circuitsvibe init my-circuit     # scaffolds my-circuit.bench.ts + AGENTS.md
$ npx circuitsvibe verify my-circuit.bench.ts
$ npx circuitsvibe verify my-circuit.bench.ts --json   # full RunRecord for agents
  • init [name] writes <name>.bench.ts (an LED driver that passes as-is) and an AGENTS.md playbook for your coding agent.
  • verify runs the ladder lint → op → tran and exits 0, 1, 2 or 3 (see exit codes).
  • The short alias cvibe accepts every command: npx cvibe verify ….

Offline or sandboxed agents#

When the agent cannot reach npm, download a single zero-dependency file and run it with Node:

standalonesh
$ curl -O https://circuitsvibe.com/circuitsvibe-standalone.mjs
$ node circuitsvibe-standalone.mjs verify x.bench.ts

The agent playbook is also published at circuitsvibe.com/llms.txt; circuitsvibe agents prints the same AGENTS.md locally.

Your first bench#

led-driver.bench.tsTypeScript
import { bench, VoltageSource, Resistor, LED } from 'circuitsvibe';

export default bench('led-driver', (tb) => {
  const v1 = tb.add('V1', new VoltageSource(5));
  const r1 = tb.add('R1', new Resistor('330'));
  const d1 = tb.add('D1', new LED());
  v1.pin('+').connect(r1.pin('1'));
  r1.pin('2').connect(d1.pin('anode'));
  d1.pin('cathode').connect(tb.gnd);
  v1.pin('-').connect(tb.gnd);

  tb.param('R1', { min: '100', max: '10k', scale: 'log' }); // sizing is the platform's job
  tb.expect.op('D1.i').toBeWithin('8m', '12m');             // spec as a test
});

Three ideas in fourteen lines: components get stable ids ('R1'), pins have names ('anode', '+'), and the spec is an assertion on a probe. tb.param hands the resistor's value to the platform — if the assertion fails, you get a verified passing range instead of a guess.

The agent loop#

An LLM agent iterates on a circuit the same way it iterates on code with a test runner:

  1. Write (or edit) the bench.
  2. Run circuitsvibe verify x.bench.ts --json.
  3. Branch on the exit code. 0 → done. 1 → the circuit is valid but the spec is not met: adjust values, preferably by applying the hint. 2 → the circuit is structurally invalid or unsolvable: fix the topology first. 3 → the bench itself or the invocation is broken.
  4. Read the diagnostic: its code is stable, its at points to the offending line, and every fix carries a confidence label.
  5. Apply the fix and go back to 2.

The ladder is fail-fast: lint runs on the pure connection graph before any solver, op solves the DC operating point, tran runs the transient. When a stage fails, later stages are reported as skipped — the agent never has to decide which of several errors is the root cause.

Bench API#

A bench file default-exports bench(name, build). The build function is lazy: it runs at elaboration time, possibly several times with different parameter overrides (--set, micro-sweeps), so keep it pure — build the circuit from its arguments and nothing else.

bench(name: string, build: (tb) => void)

Declares a testbench. name appears in every report and RunRecord.

tb.add(id: string, component: T): T

Registers a component under a stable id (letters, digits, underscore, starting with a letter — e.g. 'R1'). The id is how probes, diagnostics and --set refer to it. Ids must be unique and each instance may be registered once.

Always use the returned value. When an override for that id is active, add returns a rebuilt instance; connecting pins on the original would silently wire the wrong part (the platform refuses pins connected before add).

tb.gnd: Pin

The ground pin. Every net needs a DC path to it (see F101).

tb.name(netName: string, pin: Pin)

Names the electrical net that contains pin, so it can be probed in op assertions (tb.expect.op('out')). 'gnd' and auto-generated names (n1, n2, …) are reserved.

tb.param(id, { min, max, scale?: 'lin' | 'log' })

Declares a free parameter over a component's scalar value — see Sizing with tb.param. min < max; 'log' requires min > 0. Only Resistor, Capacitor, Inductor, VoltageSource and CurrentSource have a sweepable value.

tb.expect.op(probe) · tb.expect.tran({ tstop, dt })

Assertions — the spec as a test. See Probes & assertions and Transient measurements.

Every wired component must be registered. A part connected into the circuit but never passed through tb.add is an elaboration error (exit 3): the netlist, the hash and lint must see everything the solver sees.

Values and units#

Anywhere a value is expected you can pass a number or a string with an engineering suffix: '4.7k', '10m', '2u', '1M', '1e-6'.

m ≠ M. m is milli (10⁻³) and M is mega (10⁶): '10m' is 10 mΩ / 10 mA / 10 ms; '1M' is 1 MΩ.

Probes & assertions#

Every assertion measures a probe. The grammar is three rules long:

ProbeMeasuresExampleStages
'<id>.i'current through the component'D1.i'op, tran
'<id>.v'voltage across the component'R1.v'op, tran
'<net>'voltage of a net named with tb.name'out'op only

Automatic net names (n1, n2, …) are deliberately not addressable: name the nets you care about with tb.name('out', pin) so probes stay stable across edits.

op — DC operating point#

op assertionsTypeScript
tb.name('out', r1.pin('2'));

tb.expect.op('D1.i').toBeWithin('8m', '12m');   // min ≤ measured ≤ max
tb.expect.op('out').toBeCloseTo(3.3, 0.1);      // |measured − value| ≤ tol
tb.expect.op('R1.v').toBeAbove('1.5');          // measured > value
tb.expect.op('R1.v').toBeBelow(4);              // measured < value

Matchers return the expectation, so they chain. Each call records one assertion (a1, a2, … in report order) with the source location of the call.

Transient measurements#

tb.expect.tran({ tstop, dt }) declares a transient run — fixed step dt up to tstop (at most 5,000,000 steps) — and .probe(p) selects a component quantity ('C1.v', 'D1.i'; named nets are op-only). Matchers chain, and .probe() can be called again to assert on another probe of the same run.

tran assertionsTypeScript
tb.expect.tran({ tstop: '5m', dt: '1u' })
  .probe('C1.v')
  .toSettleWithin({ target: 5, tol: 0.02, by: '4m' }) // inside 5 V ± 2 % from 4 ms on
  .toNeverExceed(5.5)                                  // no overshoot above 5.5 V
  .probe('R1.i')
  .toStayBelow('6m', { from: '1m' });                  // after 1 ms, current < 6 mA
MatcherPasses when
toSettleWithin({ target, tol, by })from t = by to the end, the signal stays inside target ± tol·|target|. target must be non-zero and by ≤ tstop.
toNeverExceed(v)the signal never goes above v at any sample.
toStayAbove(v, { from })for t ≥ from (default: the whole run) the signal stays above v.
toStayBelow(v, { from })for t ≥ from the signal stays below v.
toRippleBelow(amp, { from })peak-to-peak ripple over t ≥ from (default tstop/2) is below amp.
toEndCloseTo(v, tol)the last sample is within tol of v.

A failed tran assertion reports measured, the time of the first violation and a short waveform excerpt around it in the RunRecord. A settleWithin that never settles reports the end-of-window value — always a finite number, never Infinity.

For a sine stimulus, set v1.acAmplitude and v1.frequency on a VoltageSource (the DC value is the offset). PULSE/PWL/PWM sources and adaptive stepping are on the roadmap.

Sizing with tb.param#

Language models are good at topology and bad at continuous sizing. tb.param delegates the number: declare the range a value may take, and when an op assertion fails the platform sweeps that range (linear or log), simulates every sample, and returns the contiguous range in which lint and all op assertions pass.

delegating R1TypeScript
tb.param('R1', { min: '100', max: '10k', scale: 'log' });
tb.expect.op('D1.i').toBeWithin('8m', '12m');

On failure the assertion carries a hint:

assertion.hintJSON
{
  "kind": "verified-param-range",
  "param": "R1",
  "passingRange": [261.016, 316.228],
  "suggestedValue": 261.016,
  "passingSamples": [261, 316.2],
  "note": "log sweep; every listed value passes ALL op assertions (simulated)"
}
  • passingRange covers only the longest contiguous run of passing samples; the exact simulated values are in passingSamples.
  • Apply it without touching the file — verify x.bench.ts --set R1=261.016 — or edit the bench. --set accepts several ids: --set R1=280,V1=5.
  • No hint in the record means no value in the declared range satisfies the spec: change the topology, not the number.
  • --no-hints skips the sweep when you only want the verdict.

Diagnostics#

Codes are permanent: they are never renumbered or reworded away, so parsers and agents can key on them. circuitsvibe explain <code> prints the long explanation with the physics behind each one.

Ranges#

RangePhaseMeaning
F1xxlint (pre-solver)structural topology
S1xxlinear solverunsolvable system
S2xxnonlinear solverNewton-Raphson
A3xxassertionsspec not met
T0xxtoolingbench authoring / platform error

Active codes#

CodeSlugSeverityWhen it fires
F101floating-neterrornet with no DC path to ground (isolated by a capacitor or current source)
F103unreached-componenterrorcomponent (or island) with no connection to the grounded circuit — the solver would silently ignore it
F104voltage-source-short / voltage-source-looperrorideal source shorted, or a loop of ideal sources (an inductor is a 0 V source at DC)
F105source-clamped-diodeerrorforward-biased diode/LED clamped directly across an ideal source with no series resistance
F106dangling-pinwarningpin with no connection at all — never blocks simulation
S101unsolvable-systemerrorsingular matrix that lint did not model (rare; please report)
S201nr-nonconvergenceerrorNewton-Raphson did not converge at the DC point — names the worst component, ΔV and its oscillation history
S202nr-nonconvergenceerrorNewton-Raphson did not converge at a transient step (a smaller dt often helps)
A301assertion-failedfailassertion failed — carries measured, expected, margin and a verified hint when tb.param is declared
T001bench-errorerrorthe bench itself threw during elaboration (bad probe, duplicate id, invalid unit string…)
T002stage-crasherrora stage crashed after elaboration — a platform bug; the RunRecord is still emitted (exit 3)

Fix confidence#

Every fix in a diagnostic or hint carries a confidence label:

verified

The platform simulated the fix and it passes all of the stage's assertions. Apply it directly.

mechanical

A deterministic transformation — not simulated, but no judgment required.

suggested

A heuristic. Reason before applying.

Two invariants hold: a fix never references a flag or capability that does not exist, and an unsimulated number is never emitted without the suggested label.

Exit codes#

CodeMeaningAgent action
0all requested stages passdone
1assertion failed — circuit valid, spec not metadjust values (apply the hint) or topology
2invalid or unsolvable circuit (F/S error)fix the structure first
3tooling error — bad usage, the bench threw, or T002fix the bench or the invocation
  • Lint always runs, even with --stage op: solving a circuit lint would reject means silently discarding components and reporting fabricated numbers.
  • firstFailure in the RunRecord is the assertion id or diagnostic code that decided the verdict.

CLI reference#

The binary is circuitsvibe; cvibe is a short alias. Output is deterministic — no timestamps, no colors in the text — so two identical runs diff cleanly.

commands
circuitsvibe init [name]                     scaffold <name>.bench.ts + AGENTS.md (default: my-circuit)
circuitsvibe verify <bench.ts> [options]     run the ladder: lint → op → tran
circuitsvibe log list [--json]              list past runs from the ledger (.circuitsvibe/runs.jsonl)
circuitsvibe log show <runId>               full RunRecord of a past run
circuitsvibe explain <code>                 long explanation of a diagnostic, e.g. explain F105
circuitsvibe catalog [type] [--json]        component datasheet + probe/assertion grammar
circuitsvibe agents                         print the agent playbook (AGENTS.md)

verify options
  --json                 emit the full RunRecord as JSON on stdout
  --set R1=280,V1=5      override scalar values without editing the bench
  --stage op,tran        run only these stages (lint ALWAYS runs)
  --no-hints             skip verified sizing hints (faster)
  --no-ledger            do not append this run to .circuitsvibe/runs.jsonl

Typical agent invocation#

terminalsh
$ npx circuitsvibe verify my-circuit.bench.ts --json > run.json
$ echo $?   # 0 pass · 1 assertion failed · 2 invalid circuit · 3 tooling error
$ npx circuitsvibe log list   # what has already been tried, after the context is gone

The ledger appends one record per run to .circuitsvibe/runs.jsonl in the working directory; log show <runId> replays any of them in full.

Custom components#

defineComponent creates a component type from a definition object. The part stamps itself into the MNA matrix through a small context, can keep internal state across transient steps, and runs in the same engine as the built-ins — in benches and in the visual simulator.

defineComponent({ name, pins, params?, stamp, setup?, onStep?, nonlinear?, draw?, label?, pinLayout? })

Returns a constructor: new MyPart({ paramName: value }). pins is the list of pin names; params maps a name to { default, unit? }.

stamp(ctx)

Called on every solve. Use ctx.stampResistance(p1, p2, R), ctx.stampConductance(p1, p2, g), ctx.stampCurrentSource(pPlus, pMinus, i), ctx.stampVoltageSource(pPlus, pMinus, vsIdx, v); read ctx.params, ctx.state, ctx.time, ctx.dt, and the last solution with ctx.voltage(pin).

setup(state) · onStep(ctx, dt) · nonlinear

setup initializes state once; onStep runs before stamp at each transient step. Set nonlinear: true when the stamp depends on node voltages so Newton-Raphson iterates.

draw(ctx2d, w, h) · label · pinLayout

Visual-simulator only: a custom canvas symbol, the label prefix (default: first three letters of name) and per-pin offsets { dx, dy }.

A two-GPIO microcontroller#

This is the component behind the MCU + LEDs example: each GPIO is a Norton equivalent (Vcc through Rout) switched by a tiny "program" in onStep.

components.jsJavaScript
const MCU = defineComponent({
  name: 'MCU',
  pins: ['gnd', 'gpio0', 'gpio1'],
  params: {
    Vcc: { default: 5, unit: 'V' },
    Rout: { default: 100, unit: 'Ohm' },
  },
  nonlinear: true,
  setup(state) {
    state.gpio0 = 0;
    state.gpio1 = 0;
  },
  onStep(ctx) {
    // Program: toggle the LEDs every 1ms
    const period = 0.002;
    const phase = (ctx.time % period) / period;
    ctx.state.gpio0 = phase < 0.5 ? 1 : 0;
    ctx.state.gpio1 = phase >= 0.5 ? 1 : 0;
  },
  stamp({ stampConductance, stampCurrentSource, params, state }) {
    const G = 1 / params.Rout;
    stampConductance('gpio0', 'gnd', G);
    if (state.gpio0) stampCurrentSource('gpio0', 'gnd', params.Vcc * G);
    stampConductance('gpio1', 'gnd', G);
    if (state.gpio1) stampCurrentSource('gpio1', 'gnd', params.Vcc * G);
  },
});

In a bench, register it like any other part — tb.add('U1', new MCU()) — and wire its pins by name. Its numeric params become part of the canonical netlist, so two electrically different custom parts never share a hash. Custom parts have no sweepable scalar, so tb.param and --set do not apply to them.

Using the visual simulator#

The simulator runs the same engine in your browser, 100 % locally. It has two surfaces that stay in sync: a canvas with a parts palette, and a code editor whose script builds the circuit. The canvas is a projection of the code; Generate Code goes the other way.

Scripting API in the editor#

The editor exposes Circuit, Ground, Junction, the nine built-in parts, defineComponent and console. Values take numbers or unit strings.

main.js — in the simulatorJavaScript
const circuit = new Circuit();
const gnd = new Ground();

const v1 = new VoltageSource(5);
const r1 = new Resistor(1000);
const c1 = new Capacitor('1u');

v1.pin('+').connect(r1.pin('1'));
r1.pin('2').connect(c1.pin('1'));
c1.pin('2').connect(gnd.pin('1'));
v1.pin('-').connect(gnd.pin('1'));

circuit.probe(c1, 'voltage');                 // 'voltage' | 'current', optional label and color
const result = circuit.analyze('transient', { timeStep: 1e-5, duration: 5e-3 });

const curve = result.probes[0].values;        // result.timePoints holds the time axis
console.log('Vc after 5τ:', curve[curve.length - 1].toFixed(3), 'V');
console.log('R1 current:', (r1.current * 1000).toFixed(3), 'mA'); // comp.voltage / comp.current
  • circuit.analyze('dc') solves the operating point; afterwards every component exposes .voltage and .current.
  • circuit.analyze('transient', { timeStep, duration }) needs at least one circuit.probe(...); it returns { timePoints, probes: [{ label, color, values }] } and opens the Chart tab.
  • Files: the editor has tabs (+ adds one, double-click renames); all files are concatenated before running. Ctrl+Enter runs.

Canvas and live simulation#

  • Palette on the left: click a tool, click the canvas to place. R rotates the selection, Delete removes it, Esc returns to select. Wires route themselves around parts; drag a wire to pin its middle segment.
  • Play (Space) starts a continuous transient. The Time slider sets simulated seconds per real second. Click a Switch or hold a Button while it runs.
  • Current appears as glowing dots moving along the wires — their speed follows the current. Wires are colored by node voltage (legend in the corner), parts glow when active, and an LED's brightness tracks its current.
  • Probes: pick the probe tool and click a pin; the oscilloscope overlay shows the traces with max / min / range / frequency / RMS, and the Chart tab keeps the full waveform.
  • Projects are saved in your browser (Project → Save), exported and imported as JSON, and the work in progress is auto-saved.
